# 原创整理类文章 Playbook

适用：**没有唯一外文原文可译**的稿件。典型三种输入——

1. 用户给参考资料链接 + 自己的笔记/截图，要求「整理成公众号文章」
2. 用户先让我做了方案/调研（产出一份 md），再说「整理成一个公众号」
3. 用户指定主题（如「硬件 AI 探索」），让我自行组织成文

与翻译类（见 SKILL.md 主干）的核心差异只有一句话：**翻译类有原文当骨架，原创类必须自己立论点。**

---

## 一、先判断：这是编译评述，还是原创整理？

| 类型 | 特征 | 文末写法 | 案例 |
|---|---|---|---|
| 编译 + 评述 | 有一篇主原文，但本地化改写、补了自己的章节 | 「本文为编译与评述，不是逐字翻译；引用的技术细节以原文为准，观点部分由编译者负责」 | Diode 篇 |
| 原创整理 | 多篇资料 + 自己的实践/笔记，没有主原文 | 「本文为实践整理与评述，非官方文档」+ 逐条列出参考文献 | 硬件 AI 探索篇 |

**不要混用**：原创整理写成编译，会让人误以为观点来自某篇权威原文；编译写成原创，等于把别人的成果当自己的。

---

## 二、动笔前必须解决的三件事

### 1. 找到一句话论点（不是主题）

主题是「硬件 AI」，论点是「先造语言、再放模型，这个顺序反了，AI 进硬件就只剩画图」。

检验标准：**把论点放到 intro 第一句，全文每个章节都要能回答「这章怎么支撑它」。** 某章答不上来就删，不要因为资料好而留。

反面案例：方案文档里十条都重要，直接搬上去就成了清单体——读者记住零条。

### 2. 结构重排，不要搬目录

方案 md 的目录是**给执行者看的**（分工具、分步骤）；文章的目录是**给读者看的**（有推进感：立论 → 证明 → 转折 → 落地 → 划界）。

硬件 AI 那篇的实际重排：

```
方案文档顺序          文章顺序
─────────────      ─────────────
KiCad 链           → ① Diode 做对了什么（拆四根柱子）
SKiDL 介绍         → ② 那个位置已有人占了（SKiDL）
目录结构           → ③ 代码怎么变成原理图（亮产物，证明闭环）
门禁脚本           → ④ 把检查串成门禁
FreeCAD 链         → ⑤ FreeCAD 侧必须换分工（转折）
FCStd 问题         → ⑥ 为什么不能当真源
几何自检           → ⑦ 真跑一遍：一个支架
FEM 坑             → ⑧ FEM 那个坑
签核边界           → ⑨ 哪些活别交给模型（表格）
启动计划           → ⑩ 两天怎么起步
```

关键动作：**把「证明闭环成立」的证据提前到第 3 章**。读者不信「代码能变电路」，后面全是空谈。

### 3. 事实核查清单（原创类比翻译类更容易出错）

翻译错了能对照原文，原创错了没人兜底。发布前逐项核：

- [ ] **版本号**：build123d 0.13.0、SKiDL 3.0.0 这类数字必须实测或查证，不能凭记忆（写错一个版本，整篇可信度归零）
- [ ] **发布日期**：「今年 10 月 16 日刚发 3.0.0」——先确认当前日期
- [ ] **许可协议**：MIT / Apache 2.0 / GPL 各不同，查 LICENSE 文件
- [ ] **工具能力边界**：如「IPC API 只覆盖 PCB 编辑器、不负责导出」——这类断言要查官方文档或 release notes，别想当然
- [ ] **个人信息**：项目作者姓名、国籍、公司所在地，核对 profile（GitHub 类尤其容易出错）

已在 SKILL.md「原文来源矩阵」里强调过 GitHub 的 profile 核对，这里同样适用。

## 三、配图：原创类的三个来源

翻译类只用官网原图；原创类通常不够，得三路凑：

| 来源 | 用法 | 图注写法 |
|---|---|---|
| **官方图**（文档站/CDN） | 能拿就拿，优先 | 「图 N｜…… 图片来自 XX 官方文档。」 |
| **自绘示意图** | 架构对比、流水线这类没有现成图的 | 「图 N｜…… 为本文作者自绘。」 |
| **自己实跑生成** | 最有说服力 | 「图 N｜…… 由本文作者用 <工具> <版本> 实际生成。」 |

**第三类优先级最高。** 硬件 AI 那篇的支架图是本機 build123d 真跑出来的（60×40×4 底板 + Ø16 孔），所以图注能写死「体积 15884.9 mm³、包围盒 60×40×34」——这些数字是真的，正好支撑文中那句「模型编不出 volume 和最小壁厚」。自己跑出来的图天然带论据。

### 自绘示意图做法

用 PIL 直接画（Box/箭头/文字），或用 matplotlib 出图再转 PNG。**不要用 SVG 里嵌文字后靠浏览器渲染**——中文字体在渲染环境里可能不可用，会变豆腐块。PIL 画完自己 Read 一遍检查：

- 文字有没有被裁切、溢出边界
- 两列是否对齐
- 中文字体是否正常（写了字体路径也可能 fallback）

### 实跑类配图做法

```python
# 建模 → 导出 SVG → playwright 渲染 → compress_images.py
# 例：build123d 的 project_to_viewport 取可见/隐藏边，ExportSVG 分两层导出
```

导出后务必 `Read` 看一眼，确认线框完整、不是空白或只有背景。

## 四、封面：AI 只画背景，标题用 PIL 叠

原创类封面常常要放**中文长标题**（如「硬件 AI 探索」+「把 Diode 流程搬进 KiCad 与 FreeCAD」）。让 ImageGen 直接渲染中文长句风险高：字形错乱、副标题挤到标题、位置不可控。

**正确做法（2026-10-27 起固定）**：

1. ImageGen prompt 里明确写「不出现任何文字或字母」，只生成带留白的背景插画
2. 取背景 → 模糊延展到 2.35:1（或直接 pad）
3. **PIL 叠加中文标题**：指定字体文件，`ImageDraw.text` 描边 + 填充

```python
from PIL import Image, ImageDraw, ImageFont
# 描边保证任何底色上都可读
for dx, dy in ((-3,0),(3,0),(0,-3),(0,3)):
    d.text((x+dx, y+dy), text, font=f, fill=(6,14,18))
d.text((x, y), text, font=f, fill=(255,255,255))
```

好处：字形绝不会错、位置完全可控、改标题不用重新生成（省积分）。

两个已踩的坑：

- **副标题紧贴标题**：两行间距要留够（main 128px 时，sub 的 y 至少差 160+），画完必须 Read 检查
- **模糊延展有竖直接缝**：paste 后对拼接边缘做一次羽化过渡，否则能看出一条直线

生成完照例去右下角 AI 水印（取上方背景条覆盖），见 SKILL.md Step 3。

## 五、正文写作硬规则

### 1. 不能有 markdown 标记

言序不解析 `**粗体**`，会原样露出星号。全文写完后统一清一遍：

```bash
sed -i 's/\*\*//g' build_payload.py   # 在构建脚本里清，再重新生成 payload
grep -c '\*' payload.json             # 确认只剩代码里的乘号
```

### 2. 数据要标注来源等级

同一篇文章里可能混着三种数字，必须让读者分得清：

| 等级 | 例子 | 写法 |
|---|---|---|
| 官方数据 | 「两周 250 个参考设计」 | 直接写，注明出自原文 |
| 实测数据 | 「体积 15884.9 mm³」 | 写明由本文作者实测 |
| 个人估算 | 「搭验证环境提效 5–20 倍」 | **必须声明「为个人估算，非实测、不构成承诺」** |

漏掉第三种声明是最危险的一类错误——读者会把估算当承诺，而它出自我的笔记或转述。

### 3. 局限章不能省

原创整理类没有「原文权威」背书，可信度全靠自己给自己挑毛病。硬件 AI 那篇写了五条局限（仿真过不等于制造过、参考设计≠产品设计、库覆盖决定上限、效率数字是自述、自有语言的锁定风险）。

**这是这类文章的信用来源**，砍掉它，全文就变成软文。

### 4. 划界表

涉及「AI 能做什么、不能做什么」的主题，把判断标准固化成一张表（环节 / 能不能交给模型 / 原因）。判据要一句话能说清，例如：

> 凡是出错后要重新花钱做物理件的地方，都不该由模型单独决定。

表格比散文更容易被读者记住，也方便后续复用这条判据。

## 六、文末参考文献格式

原创类必须有独立的「参考文献与说明」章，逐条列：

```
1. 原文/项目名. 文章标题. URL
2. 工具名 项目与文档（许可，版本号 发布于 YYYY-MM-DD）：URL ／ 备用 URL
...
N. 配图出处：图 1、图 2 来自 XX 官方文档，版权归原作者；
   图 N 由本文作者用 <工具> <版本> 实际生成；图 M 为本文作者自绘。
说明：本文为实践整理与评述，非官方文档。文中工具版本与接口状态截至
YYYY 年 MM 月，<某时间点/路线图> 以官方为准。仅供学习交流。
```

三条不能少：

- **配图出处逐张交代**（哪张是官方、哪张是自己跑的、哪张是自绘）
- **时间锚点**（「截至 2026 年 10 月」——工具生态变化快，没有锚点的断言会过期）
- **非官方声明**

## 七、完整流程（原创整理类）

```
1. 收资料（链接 / 笔记 / 截图 / 已有方案 md）
2. 立一句话论点 —— 写不出就先别动笔
3. 结构重排：立论 → 证明 → 转折 → 落地 → 划界（不搬方案目录）
4. 事实核查：版本号 / 日期 / 许可 / 能力边界 / 人名地名
5. 配图：官方 → 自绘 → 实跑生成（实跑优先级最高）
6. 封面：ImageGen 只出背景（prompt 写明不出现文字）→ PIL 叠中文标题
7. 建 payload → validate_payload.py → 清 markdown 标记 → 通读查错字
8. create_article → publish_article（neon）→ curl -I 验图
9. 更新 published-index.md + 工作区索引
10. 提醒：去草稿箱确认图齐全 + 群发人工
```

第 7 步的通读尤其重要：言序无改稿接口，一个异体字（如「邉」）或一个漏字（「封装与散」）就得整篇重建重发。已发生过两次。
